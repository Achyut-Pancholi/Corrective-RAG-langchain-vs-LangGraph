PART 1: THE BIG PICTURE — WHAT IS THIS PROJECT AND WHY DOES IT EXIST?
================================================================================

The Problem With Standard AI Search (Why This Project Matters)
--------------------------------------------------------------
Imagine you ask an AI assistant: "What wavelength of light does Lumicite 
crystal absorb?". The AI searches its knowledge base (a vector database), 
finds the most "similar" documents, and blindly generates an answer using 
those documents — even if they're completely wrong or irrelevant.

This is called standard Retrieval-Augmented Generation (RAG). It has a 
fundamental flaw: it NEVER checks whether the documents it retrieved are 
actually useful. It just assumes they are. So if your question is ambiguous 
and retrieval returns garbage documents, the AI will confidently generate a 
garbage answer — this is called "hallucination".

Your Solution: Corrective RAG (CRAG)
-------------------------------------
You built a system that adds a self-correction loop. Before generating any 
answer, the system GRADES the retrieved documents. If they are not good enough,
it actively REWRITES the user's question to be clearer and more specific, then 
searches again. Only when it finds good documents does it generate an answer.

This is Corrective RAG (CRAG), and you built it using a framework called 
LangGraph which enables graph-based, cyclical AI workflows.

The Proof of Concept (POC) Structure
---------------------------------------
You built TWO systems side-by-side so your mentor can see the difference:
  - Flow A (LangChain Baseline): Standard, broken linear RAG.
  - Flow B (LangGraph CRAG): Smart, self-correcting RAG.

Both share the same vector database, the same LLM, and the same documents.
The ONLY difference is the orchestration logic (how they use them).

The Streamlit web UI lets you switch between both and see the results live.

2.1 — What is RAG? (Retrieval-Augmented Generation)
-----------------------------------------------------
RAG = Retrieval + Generation combined.

THEORY:
LLMs (Large Language Models) are trained on data up to a certain date. They 
don't know about your specific documents, your company's internal data, or 
recent events. RAG solves this by giving the LLM a relevant "context" (document 
snippets) at the time of answering.

HOW IT WORKS (Step by Step):
  Step 1 — Ingestion (Done once, offline):
    - Your documents (PDFs, text files) are loaded.
    - Each document is split into smaller "chunks" of text.
    - Each chunk is converted into a list of numbers called an "embedding" 
      (a vector). This represents the meaning of the text mathematically.
    - All these vectors are stored in a special database called a 
      "Vector Store" (in your case, Chroma DB).
  
  Step 2 — Retrieval (At query time):
    - When a user asks a question, the question is ALSO converted into a vector.
    - The vector store finds the document chunks whose vectors are most 
      mathematically similar (close in vector space) to the question's vector.
    - These matching chunks are called the "retrieved documents" or "context".

  Step 3 — Generation (At query time):
    - The retrieved documents + the original question are packaged into a 
      "prompt" and sent to the LLM (your AI model).
    - The LLM reads the context and generates a grounded, specific answer.

THE LIMITATION:
  Standard RAG has no feedback loop. If retrieval returns wrong documents,
  the LLM will still try to answer using that bad context. It cannot self-heal.

2.2 — What is CRAG? (Corrective RAG)
---------------------------------------
CRAG adds a GRADING + CORRECTION step between Retrieval and Generation.

HOW IT WORKS:
  After retrieving documents:
    - Each document is scored by the LLM: "Is this document relevant to 
      the user's question? Yes or No?"
    - If YES: proceed to generate the answer normally.
    - If NO: do NOT generate yet. Instead, REWRITE the user's question to 
      be more specific, and go back to Step 2 (retrieve again with the 
      better query).
    - This loop can repeat up to MAX_RETRIES times (set to 2 in your project).
    - If retries are exhausted, it forces generation with whatever it has.

2.3 — What is a Vector / Embedding?
--------------------------------------
THEORY:
An embedding is a mathematical representation of text as a list of numbers 
(a vector in high-dimensional space). The key property is that text with 
SIMILAR MEANING will produce vectors that are CLOSE TOGETHER in this space.

EXAMPLE:
  "The cat sat on the mat." -> [0.12, 0.45, -0.33, 0.71, ...]
  "A feline rested on a rug." -> [0.14, 0.43, -0.30, 0.69, ...]  <- Very close!
  "The stock market crashed." -> [0.89, -0.12, 0.55, -0.40, ...]  <- Far away!

In your project, you use a model called "all-MiniLM-L6-v2" from HuggingFace 
to create these embeddings. It converts any text to a 384-number vector.
The model runs locally on your machine — no API call needed.

2.4 — What is a Vector Store / Database?
------------------------------------------
A vector store is a specialized database designed to store and search 
high-dimensional vectors very efficiently.

You use CHROMA DB. When you search it with a query vector, it uses an 
algorithm called "cosine similarity" (or sometimes euclidean distance) to find 
the stored vectors that are most similar (closest in angle) to your query.

The result is the "top K" most relevant document chunks (k=2 in your project).

2.5 — What is LangChain?
--------------------------
LangChain is a Python framework for building LLM-powered applications. 
It provides:
  - Connectors to LLMs (OpenAI, Groq, Anthropic, etc.)
  - Connectors to Vector Stores (Chroma, Pinecone, FAISS, etc.)
  - Document loaders (PDF, TXT, CSV, etc.)
  - A "chain" syntax called LCEL (LangChain Expression Language) using the 
    pipe operator (|) to connect components into a linear pipeline.

LCEL EXAMPLE (how you used it in langchain_rag.py):
  chain = Prompt | LLM | OutputParser
  This means: "Send the prompt to the LLM, then parse its text response."

2.6 — What is LangGraph?
--------------------------
LangGraph is built on top of LangChain. While LangChain creates linear chains 
(A -> B -> C), LangGraph allows you to build GRAPHS — workflows with:
  - Multiple nodes (each node = a function that does some work)
  - Conditional edges (routing: "go to node B OR node C depending on a condition")
  - Cycles (going backwards: "after node C, go back to node A")

These properties are essential for implementing CRAG, because CRAG needs 
a feedback loop (it can go backwards from "Rewrite" to "Retrieve").

KEY CONCEPTS in LangGraph:
  - StateGraph: The main graph object. You define it and add nodes/edges to it.
  - GraphState (TypedDict): A Python dictionary that persists data as it flows 
    through the graph. Every node reads from and writes back to this state.
  - set_entry_point(): Defines which node runs first.
  - add_edge(): Defines a fixed transition (A always goes to B).
  - add_conditional_edges(): Defines a dynamic transition based on a function.
  - compile(): Locks the graph structure and returns a runnable "app".
  - END: A special sentinel that tells the graph "we're done here".

2.7 — What is Groq?
---------------------
Groq is a company that provides an API for fast LLM inference. Their hardware
(LPU - Language Processing Unit) is extremely fast at running LLM models.

You use Groq because:
  1. It has a generous free tier (no cost for this POC).
  2. It is fast — responses come back in under 1 second.
  3. It integrates seamlessly with LangChain via langchain-groq.

The specific model you use: "openai/gpt-oss-20b"
  - This model is accessed through Groq's inference API.
  - Temperature=0 means deterministic/reproducible answers (no randomness).

2.8 — What is Streamlit?

Streamlit is a Python library for building interactive web applications 
with zero HTML/CSS/JavaScript knowledge. You write pure Python and 
Streamlit renders it as a web page.

Key Streamlit concepts used in your app.py:
  - st.title(), st.markdown(): Display text on the page.
  - st.radio(): Creates the "Select Flow" toggle button.
  - st.text_input(): Creates the question input box.
  - st.button(): The "Ask Question" button.

  - st.write(), st.subheader(), st.divider(): Layout helpers.
  - st.expander(): Creates a collapsible section (used for Sources).
  - st.error(), st.warning(), st.exception(): Shows error messages.

2.9 — What is LangSmith?
--------------------------
LangSmith is an observability platform built by LangChain. 
When enabled, it automatically captures:
  - Every LLM call (input prompt, output, token count, latency)
  - Every LangGraph node execution and its timing
  - Full execution traces for debugging

To enable it, you add these to your .env file:

  LANGCHAIN_ENDPOINT=https://api.smith.langchain.com
  LANGCHAIN_API_KEY=your_langsmith_api_key

NO CODE CHANGES NEEDED — LangChain reads these env vars automatically.

WHAT IS A TypedDict?
  TypedDict is from Python's typing module. It creates a dictionary subclass 
  with a FIXED SCHEMA — it defines what keys are allowed and what type each 
  value must be. It's like a contract for the dictionary.
  
  COMPARISON:
    Plain dict:      {"question": "hello", "count": 5}  <- no rules
    TypedDict:       GraphState specifies EXACTLY what keys exist and their types.
  
  WHY USE TypedDict INSTEAD OF A REGULAR CLASS (dataclass)?
    LangGraph's StateGraph REQUIRES the state to behave like a dictionary 
    because it MERGES partial updates from each node. When a node returns 
    {"documents": some_list}, LangGraph merges that into the full state 
    dictionary — updating only the "documents" key. A regular class object 
    doesn't support this merge-update behavior natively.

Line 1: from typing import TypedDict, List
  TypedDict: The base class for our schema.
  List: Used to annotate list types (e.g., List[Document]).

Line 2: from langchain_core.documents import Document
  LangChain's Document class represents a piece of retrieved text.
  It has two important attributes:
    .page_content: str = The actual text of the chunk
    .metadata: dict = Information about the source, e.g.:
      {"source": "paper1.pdf", "page": 3}

Line 3: from src.utils.formatting import TraceStep
  Imports the TraceStep dataclass defined in formatting.py.
  Used for the execution_trace list (the UI log).

Lines 10-15: The Fields of GraphState

  question: str
    The original user question, EXACTLY as typed. This NEVER changes.
    Even if the query gets rewritten, we keep the original here for display 
    and for generating the final answer (we always answer the original question,
    not the rewritten search query).
    Example: "tell me about the satellite mapping stuff"

  documents: List[Document]
    The documents retrieved from Chroma. This list CHANGES as the graph runs:
    - After retrieve_node: Contains TOP_K documents (e.g., 2 docs)
    - After grade_documents_node: Only contains the RELEVANT docs (could be 0-2)
    - If grading passes: These docs are used for generation.
    - If grading fails: Empty list [], triggering the rewrite loop.

  generation: str
    The final text answer from the LLM. Empty string "" until generate_node 
    runs. This is what appears in the "Answer" section of the UI.

  retry_count: int
    A counter. Starts at 0. Incremented by 1 in rewrite_query_node each time.
    Checked in conditional_routing against MAX_RETRIES.
    If retry_count >= MAX_RETRIES, we stop retrying and force generation.

  rewritten_query: str
    Starts empty "". The rewrite_query_node fills this with a new, better 
    search query. retrieve_node checks this: if it's non-empty, use it instead 
    of the original question. This is the mechanism that enables the retry loop.

  execution_trace: List[TraceStep]
    A log of what happened, step by step. Each node appends to this list.
    The UI renders this as a sequence of labeled steps with icons.
    This is what makes the difference between the two flows VISIBLE to a user.
    Standard RAG: Just 3 steps (received, retrieved, generated)
    CRAG with rewrite: 5+ steps (received, retrieved, graded:insufficient, 
    rewritten, retrieved again, graded:ok, generated)

Lines 10-12: def format_docs(docs)
  Takes a list of LangChain Document objects.
  Extracts .page_content from each one.

    - Large enough to contain a complete thought or answer

    the next chunk.

    Band 1 covers wavelengths of 443 nanometers..."
    
    The answer is self-contained in Chunk 2. This is why overlap is critical.

THE "FACTORY PATTERN" DESIGN PRINCIPLE:

Lines 9-13: ChatGroq(...)
  Creates a connection to the Groq API.

    Authenticates every API request. Without this, Groq would reject all calls.

    Tells Groq WHICH model to run. Currently "openai/gpt-oss-20b".
    By reading from config (not hardcoding), changing the model in .env 
    immediately changes behavior without touching this file.
  
  temperature=0:
    Controls the RANDOMNESS of the LLM's output.
    
    TECHNICAL EXPLANATION:
      LLMs predict the next word as a probability distribution. At each step, 
      the top candidate words have different probabilities. Temperature scales 
      this distribution:
        temperature=0: Always pick the highest-probability word. 100% deterministic.
        temperature=1: Sample from the distribution naturally (some randomness).
        temperature=2: Flatten the distribution, making unlikely words more likely.
    
    WHY temperature=0 HERE?
      For GRADING, you need "yes" or "no" — not "maybe" or "sort of".
      For QUERY REWRITING, you need a focused technical query — not a creative one.
      For ANSWERING, you need factual accuracy — not creative storytelling.
      Determinism is correct for all three use cases.

    L6: Uses 6 transformer layers (original BERT had 12, making MiniLM faster).

    For a POC comparing orchestration strategies, local embeddings are perfectly adequate.

  In LangChain, a Retriever is a standardized interface (abstract base class)

    .invoke(query: str) -> List[Document]
  
  Any LangChain component that needs to search for documents accepts a 
  Retriever — not a specific vector store class. This is the "Program to 
  an interface, not an implementation" principle.

  Gets the cached/loaded Chroma instance from vector_store.py.

  Retriever object. Chroma is a concrete implementation; Retriever is the

    "k": 2 means "return the 2 most similar document chunks".
    "k" stands for "k-nearest-neighbors" — a fundamental algorithm in 
    machine learning for finding the k closest points in a dataset.

  we query that database). If you wanted to change the search strategy — for 
  example, switch from "top k" to MMR (Maximum Marginal Relevance, which 
  balances similarity with diversity of results) — you only change retriever.py.

    multiple values simultaneously.

    RESULT: A fully formatted prompt string ready to send to the LLM.

  STEP 3: llm
    The formatted prompt is sent to ChatGroq (Groq API).
    RESULT: An AIMessage object containing the LLM's response text.

  STEP 4: StrOutputParser()
    Extracts just the text string from the AIMessage.
    AIMessage has attributes like .content (the text) and .response_metadata.
    StrOutputParser pulls out just the .content string.
    RESULT: A plain Python string containing the answer.

  def rewrite_query_node(state: GraphState):
      question = state["question"]           <- Rewrite from ORIGINAL question
      retry_count = state.get("retry_count", 0) + 1   <- Increment counter
      
      llm = get_llm()
      chain = REWRITE_PROMPT | llm | StrOutputParser()
      rewritten_query = chain.invoke({"question": question})
      
      return {"rewritten_query": rewritten_query, "retry_count": retry_count, ...}

  question = state["question"]
    We always rewrite based on the ORIGINAL question.
    We don't iteratively rewrite the rewritten query (that could drift 
    far from the user's intent).

    Gets current retry_count (or 0 if not set) and increments by 1.
    This is the safety counter. After this function returns, the state 
    will have retry_count = 1 (first rewrite) or 2 (second rewrite), etc.

  chain.invoke({"question": question})

    The LLM outputs a new, improved search query string.
    rewritten_query is a PLAIN TEXT string — no markdown, no explanation.

  On the next call to retrieve_node, it will find this non-empty string 
  and use it for retrieval.

THE ROUTER: conditional_routing (lines 81-95)
----------------------------------------------
  def conditional_routing(state: GraphState):
      documents = state["documents"]
      retry_count = state.get("retry_count", 0)
      
      if documents:
          return "generate"
      
      if retry_count >= MAX_RETRIES:
          return "generate"
          
      return "rewrite"

  This function returns a STRING. LangGraph calls this function after 
  grade_documents_node and uses the returned string to look up the next 
  node in the mapping dictionary provided to add_conditional_edges().

  if documents: return "generate"
    If the list is non-empty (has relevant docs) -> go generate.
    This is the HAPPY PATH — found good documents, proceed.

  if retry_count >= MAX_RETRIES: return "generate"
    We've already rewritten MAX_RETRIES times.
    Give up on finding good documents. Generate with empty context.
    The LLM will say "I don't know" — which is honest and correct behavior.
    THIS IS THE CIRCUIT BREAKER — prevents infinite API calls.

  return "rewrite"
    Documents is empty, but we haven't hit the limit.
    Go rewrite the query and try again.

PART 4: THE DATA — YOUR KNOWLEDGE BASE

4.1 — data/documents/
  Contains the 12 Kaggle PDF research papers (dataset: saibhossain/rag-practice).
  These papers cover topics including:
  - Satellite remote sensing and Earth observation
  - Terrain classification and land cover mapping
  - Machine learning for geospatial analysis
  - Atmospheric correction and preprocessing pipelines
  - Spectral band analysis (including Sentinel satellite instruments)

  WHY THIS DATASET?
    Early testing used small synthetic text files (hand-written dummy documents 
    about "Aethelgard" and "Lumicite crystals"). The problem: the synthetic 
    corpus was SO small and distinct that even standard RAG never failed.
    With only 5-8 document chunks, the vector space is tiny and keyword 
    matches are always perfect.
    
    Moving to 12 dense research PDFs creates 1,245 chunks with overlapping 
    topics and vocabulary. Now a vague query genuinely fails to retrieve the 
    right chunk, demonstrating the real-world problem CRAG solves.

4.2 — data/chroma_db/
  Auto-generated by Chroma on first app run. Contains:
  
  - chroma.sqlite3: The main SQLite database file. Stores document metadata,
    collection information, and other relational data.
  - Binary segment files (*.bin): The HNSW vector index.
  
  WHAT IS HNSW?
    Hierarchical Navigable Small World. The algorithm Chroma uses internally 
    to search vectors efficiently. It's a graph-based index where vectors 
    that are similar to each other are connected. Search starts at a random 
    entry point and "navigates" through the graph toward increasingly similar 
    neighbors. Much faster than comparing the query against all 1,245 vectors.

4.3 — The Numbers You Should Know
  12 PDFs -> (many pages) -> 1,245 chunks (after RecursiveCharacterTextSplitter)
  Each chunk -> 384-dimensional embedding vector (from all-MiniLM-L6-v2)
  Each query: retrieves top 2 chunks (TOP_K=2)
  First run: ~85 seconds to embed everything
  Subsequent runs: ~0.03 seconds to load from disk

PART 7: COMPLETE Q&A — EVERY QUESTION YOUR MENTOR MIGHT ASK

Q: What is the difference between LangChain and LangGraph?
A: "LangChain builds linear pipelines using the LCEL pipe syntax — data flows 
one direction from component to component. LangGraph extends this with the 
ability to build state machines — graphs where nodes have conditional edges 
and can cycle back to previous nodes. For CRAG, we need a feedback loop: 
the graph must be able to go backwards from Query Rewrite to Retrieve multiple 
times. That's impossible in standard LangChain but straightforward in LangGraph."

Q: Why Chroma over FAISS or Pinecone?
A: "FAISS is an in-memory only library — fast but requires re-loading on every 
process restart. Pinecone is a managed cloud service — excellent for production 
but costs money and requires an account setup. Chroma runs locally, supports 
on-disk persistence natively, and requires zero configuration beyond specifying 
a directory path. For a free POC where setup speed matters, Chroma was the 
optimal choice."

Q: What embedding model did you use and why?
A: "I used all-MiniLM-L6-v2 from HuggingFace. It's a distilled transformer 
model — 'MiniLM' meaning compressed from a larger model, 'L6' meaning 6 
transformer layers. It produces 384-dimensional embeddings. I chose it because 
it runs completely locally with no API calls, it's free, and it's widely used 
as the industry benchmark embedding model for RAG systems."

Q: What does temperature=0 mean?
A: "Temperature controls the randomness distribution of the LLM's output. At 
temperature=0, the model always selects the highest-probability next token — 
making the output fully deterministic and reproducible. This is important for 
our grading step (we need consistent yes/no decisions) and query rewriting 
(we need focused, technical outputs). Higher temperatures introduce creative 
variation, which is useful for creative writing but harmful in a structured 
retrieval pipeline."

Q: How do you prevent infinite retry loops?
A: "The GraphState includes a retry_count integer that starts at zero. Each 
time rewrite_query_node executes, it increments this counter. In the 
conditional_routing function, before routing to the rewrite node, I check 
if retry_count >= MAX_RETRIES (currently 2). If the limit is reached, we 
force routing to the generate node regardless of document quality. The 
generate node then handles empty context by passing 'No relevant context found' 
to the RAG_PROMPT, which responds 'I don't know based on the provided documents.'"

Q: What is the execution trace in the UI?
A: "I implemented a logging system using a TraceStep dataclass. Each node 
appends a TraceStep to the execution_trace list in GraphState. A TraceStep 
has a name, a status (success/warning/error), and optional details. At the 
end of graph execution, app.py reads this trace and renders it with icons: 
check for success, warning sign for insufficient documents, and cross for 
errors. This makes the self-correction behavior completely transparent to users."

Q: Why did you move from synthetic documents to a Kaggle dataset?
A: "During initial testing, I noticed that standard RAG and CRAG were giving 
identical results for most queries. The root cause was dataset size — with 
only 5-8 synthetic document chunks, the vector space was too sparse. Any 
query returned correct documents because there were so few alternatives. 
Moving to 12 research PDFs (1,245 chunks) created the complex, crowded 
vector space where vague queries genuinely retrieve wrong documents, making 
the CRAG correction loop both necessary and demonstrably valuable."

Q: What would you change for production?
A: "Several improvements: First, replace Chroma with a managed vector database 
like Pinecone or pgvector for scalability and reliability. Second, add an 
API layer (FastAPI) so other applications can integrate with the RAG system. 
Third, implement document versioning — currently, adding new documents requires 
deleting and rebuilding the entire Chroma database. Fourth, add monitoring 
and alerting beyond LangSmith (Prometheus metrics, error rate alerts). Fifth, 
add user authentication and usage logging."

Q: How does chunking affect RAG quality?
A: "Chunk size directly impacts retrieval precision. Smaller chunks (e.g., 300 
characters) are more focused but may lose context. Larger chunks (e.g., 2000 
characters) carry more context but are less precise in vector search results. 
The 200-character overlap ensures continuity across chunk boundaries, preventing 
information loss when a key sentence spans two chunks. The choice of 1000 
characters with 200 overlap is a standard starting point that balances 
specificity and context preservation."

Q: What is cosine similarity and why is it used for vector search?
A: "Cosine similarity measures the ANGLE between two vectors in high-dimensional 
space, regardless of their magnitude (length). Two vectors pointing in the same 
direction have a cosine similarity of 1.0 (identical direction = same meaning). 
Two perpendicular vectors have 0.0 (unrelated). It's used for text similarity 
because the magnitude of an embedding vector can vary based on word count 
without changing meaning, while the direction captures the semantic content. 
Measuring angle is more robust than measuring raw distance."

Q: How is LangSmith integrated?
A: "LangSmith requires zero code changes. LangChain automatically checks for 
four environment variables: LANGCHAIN_TRACING_V2=true (enables tracing), 
LANGCHAIN_ENDPOINT (the API URL), LANGCHAIN_API_KEY (authentication), and 
LANGCHAIN_PROJECT (the project name to group traces under). When these are 
set in the .env file, every LLM call, every LangGraph node execution, latency 
breakdowns, and token counts are automatically captured and sent to the 
LangSmith dashboard."

Q: Why is the rewrite done from the original question and not the previous rewrite?
A: "Iteratively rewriting a rewrite would cause semantic drift — each rewrite 
might move further from the user's original intent. The original question 
captures what the user ACTUALLY wants. We always rewrite FROM that anchor, 
not from an intermediate reformulation. This ensures we're still trying to 
answer the same question, just with better search terms."

Q: What is TypedDict and why use it instead of a dataclass?
A: "TypedDict creates a dictionary with a declared schema — specific keys with 
specific types. I used it for GraphState specifically because LangGraph's 
state management requires dictionary-like behavior. When a node returns a 
partial state update like {'documents': some_list}, LangGraph merges that 
partial dict into the full state dictionary. A dataclass would require a 
full object replacement, losing any fields not included in the update. 
TypedDict's dictionary behavior enables the incremental merge semantics 
that LangGraph relies on."

Q: The app shows 'ConnectionResetError [WinError 10054]' in the terminal sometimes. 
   Is this a bug in your code?
A: "No. This is a known, documented issue with Streamlit's underlying networking 
library (Tornado) on Windows. It occurs when the browser tab is refreshed or 
closed while the server has an open connection. Windows' networking stack 
sends a RST (reset) packet that Tornado's asyncio event loop doesn't handle 
gracefully on Windows. It appears as an error in the terminal but does not 
affect the application logic, the RAG pipeline, or any user functionality. 
It can be safely ignored."
